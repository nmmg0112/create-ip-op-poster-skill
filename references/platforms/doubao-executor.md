# 豆包 Seedream 5.0 Pro 杂志编辑式执行合同

本文件是豆包中的自包含执行说明。用户不需要复制长启动 Prompt、模型链接或平台参数，也不需要知道适配器存在。

## 自动开始

用户上传本 Skill 压缩包并说“帮我安装并告诉我怎么使用”“用这个 Skill 帮我做海报”或类似自然表达后，自动发送一次新手开场白：先说明人物肖像质量决定海报主视觉，案例截图能帮助提取达人真实内容玩法；再请用户上传人物／动物原图，并可顺手补充主题／Brief、案例、喜欢的风格、文字密度和必须出现的文字。

资料不全也可以先发人物。已有可用素材时直接整理，不重复开场白，也不要求用户按模板重填。

## 模型硬门禁

豆包中的每一次生成式图片操作——包括人物素材预览和正式海报——都先显式调用 [Seedream 5.0 Pro](skill://seedream-50?type=2&id=360075272194)。不得只在 Prompt 中写模型名称；文字声明不代表模型已加载。

执行顺序固定为：

```text
识别为豆包
  -> 调用 skill://seedream-50?type=2&id=360075272194
  -> 核验 model_skill_loaded
  -> 告知“本次生图模型：Seedream 5.0 Pro”（不等待确认）
  -> creative-design 在平台实际可用时用于视觉判断
  -> 继续人物处理或正式海报生成
```

`model_skill_loaded` 只有平台回执、工具状态或等价直接证据时才能写 `true`；看不到证据时写 `NOT_VERIFIABLE`，不能假装成功。

若平台确认 Seedream 5.0 Pro 当前不可用，说明平台实际显示的原因，不猜测一定是充值、额度或权限。随后用一句话说明：改用较低或未知模型，可能明显降低人脸一致性、案例截图和中文准确度，也可能使画面更像模板或 PPT。给出两个普通选项：

- `切换／开通后继续`（推荐）
- `继续用当前模型`

不得静默降级。只有用户在看到风险后明确回复 `继续用当前模型`，本轮才可记录 `downgrade_approved: true` 并继续；该同意只对当前这次操作有效。每次记录：

```yaml
requested_model: Seedream 5.0 Pro
model_skill_uri: skill://seedream-50?type=2&id=360075272194
model_skill_loaded: true | false | NOT_VERIFIABLE
actual_model: Seedream 5.0 Pro | platform-reported-model | NOT_VERIFIABLE
downgrade_approved: true | false
```

模型可用性提示是执行条件，不是第三个内容确认点。

## 用户流程

```text
读取 Skill
  -> 自动开场白
  -> 建立稳定人物编号
  -> 显式调用 Seedream 5.0 Pro 处理人物素材
  -> 展示一张横版白底组合预览
  -> 等待“人物没问题”
  -> 固化 ApprovedPersonAssetSet
  -> 读取 Brief、案例和视觉偏好
  -> 给出两个内容／视觉方向
  -> 等待“选 1 生成”
  -> 建立当前 LockedPosterSpec
  -> 编译豆包杂志编辑式最少充分 Prompt
  -> 附上 ApprovedPersonAssetSet 和案例原图
  -> 显式调用 Seedream 5.0 Pro 正式生图一次
  -> 查看实际成图并 QA
  -> 用户通过后建立 PosterVersionLock
```

不得增加排布稿、完整 Prompt 或技术路线确认。

## 人物素材绑定

收到多张图片后建立稳定人物编号 `P01、P02……`，同时记录公开昵称、每张图中的主体数量、不可拆分组合和所选版本。人物预览只用于确认长相、数量、身体完整性、大小和边缘，不锁定最终海报排布。

用户回复 `人物没问题` 后固化 `ApprovedPersonAssetSet`。正式调用不能只写昵称或外貌描述：

- `unified-ensemble`：附上用户批准的群像／预览；
- `grouped-by-play`：附上各组对应的批准独立人物素材；
- `hybrid-hero-groups`：同时附批准主群像和所需独立人物；
- `single-hero`：附批准单人原图或预览。

调用前逐一核对附件中的 `Pxx`、人数、组合关系和 `user_approved: true`。缺图、版本不一致或无法实际附图时停止生成，不用文字描述替代。

## 当前锁定版本

`选 1 生成` 后建立唯一 `LockedPosterSpec`：批准人物、16:9 画幅、主题背景、玩法及成员、第一视觉、人物模式、文字密度、颜色／材质／光线／景深／动势、阅读顺序、案例／Logo／固定文字、参考语法、禁用项和正式生图次数。

正式生成只使用当前锁定版本，不把整段聊天、已否决方案、旧要求、平台操作说明和重复禁令传给模型。用户改变主题、玩法、整体风格或构图时创建新的锁定版本，不能混用新旧方向。

## 豆包视觉稳定模式

豆包默认使用 **“大标题＋人物主视觉＋案例拼贴＋玩法说明”** 的杂志编辑式构图。标题、人物与案例可以跨区、交叠和穿插，通过裁切、尺度反差、前中后景、色块节奏和视线方向形成完整画面。多人默认使用批准群像做中心或右侧主视觉；单人改为单一明星／达人主视觉。配色、标题字体、材质、光线和拼贴语言随 Brief 与用户偏好变化，因此这不是固定坐标模板。

首张正式海报即应包含：

- IP／项目大标题和一句主题文案；
- 一至两句精炼项目背景；
- `ApprovedPersonAssetSet` 中的批准人物主视觉；
- 用户提供且适合进入海报的四至六张真实案例截图；少于四张时按实际数量，不虚构补齐；
- 每个玩法的标题、对应成员和一至三行说明；
- 已提供且要求出现的 Logo、商务信息、报价或权益。

玩法说明不限制为一句话。根据中等或高信息密度，在一至三行内优先写清：

1. 具体场景或人物关系；
2. 动作、挑战、互动、冲突或反转；
3. 产品／项目如何自然进入；
4. 有空间时补案例依据、合作价值或内容结果。

案例不是边角装饰。每张案例应靠近对应玩法，或用编号、标题色、引线、视线与场景关系建立可读映射。人物仍大于案例，不得缩成卡片角落的小头像。

禁止把数码、科技等 Brief 自动翻译成满屏玻璃舱、全息 UI、霓虹控制室或等宽卡片墙。需要“科技感”时，优先使用真实行业场景、克制冷色、金属／玻璃材质、展陈灯光、速度动势、摄影裁切和空间景深。不能用代码、SVG、规则矩形或系统字体承担视觉设计。

## 一次生成与修订控制

`选 1 生成` 只授权一次正式完整海报生成。第一张正式产物就是带主题、人物、玩法、案例和商务信息的 16:9 横版完整海报；不先做竖版、排布稿、空白底图、头像网格、无字中间图或程序化信息页。

禁止连续制作“新版—无字底图—代码叠字版—聚合底图—精装修版”。若正式成图失败，先指出具体失败项；只有用户明确要求重做时，才建立新的 `LockedPosterSpec` 并再调用一次。不能把一次修改授权扩展成多次试图。

用户已通过第一版后建立 `PosterVersionLock` 并保留成功文件。只改名字、Logo、固定中文、报价、权益、案例或单个标签时做局部修改，不得把整张图重新生成；平台无法精确局部修改时直接说明。

## 实际成图 QA

必须查看最终图片和调用记录。下列任一项均为 `FAIL`：

- `actual_model` 与平台证据不符，或发生未获同意的降级；
- 正式调用没有实际附上与 `ApprovedPersonAssetSet` 对应的批准图片；
- 输出不是批准的 16:9 横版；
- 人物被缩成卡片插图，或发生错脸、漏人、重复、串脸；
- 没有案例与玩法的可读对应，或玩法缺少具体场景、动作和产品进入；
- 画面呈现 PPT 式等权模块、规则卡片墙、空背景或大块无意义留白；
- 中文乱码、虚构数据、案例严重变化，或用户无法直接预览成图。

只在实际证据足够时写 `PASS`；无法核验模型、人脸或案例时写 `NOT_VERIFIABLE`，不能自我表扬替代检查。
